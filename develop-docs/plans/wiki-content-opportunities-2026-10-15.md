### A1：一个列表为什么要等十秒

**读者问题：** 只是查询一页机构列表，为什么会慢到影响使用？

**原始材料：** S114、S187、S188。

记录把原因定位到循环访问数据库，修改方向是批量读取后在内存中组装。2026-01-04 发布记录写明机构列表由 8～15 秒降到 1.5～3.5 秒；次日记录写明下单页面查询学校由 15 秒降到 1.7 秒。附件还有新旧节点的请求日志对照。

**建议结构：** 页面现象 → 查清列表额外取了什么 → 循环查询带来的成本 → 批量取数和组装 → 列表与详情的职责 → 两个入口分别验证。

**待补材料：** 修改前后代码、一次请求的 SQL 次数、分页与数据规模。发布记录中的耗时应注明是当时的现场观测；测试环境单次浏览器请求截图不能替代生产环境统计。

建议文件：`docs/lab-tech-exploration/database-middleware/list-query-n-plus-one-retrospective.md`。

### A2：页面时间正常，数据库却错了

**读者问题：** 为什么改正 JDBC 时区之后，原来正常的页面反而少了几个小时？为什么有些记录差七小时，有些差八小时？

**原始材料：** S228、S271、S230、S234。

记录包含 `String`、`Date`、`LocalDateTime`、MySQL `now()` 的对照，以及 `cast(... as char)` 与类型化读取的差异。生产修复分为配置切换与历史数据修复，另有临时服务对照页面、按字段修正和 7/8 小时差异的记录。

**建议结构：** 页面异常 → 区分数据库原值、Java 对象和接口显示 → 最小实验矩阵 → 配置切换 → 按字段及时间范围修复历史数据 → 检查下载凭证和跨系统调用。

**待补材料：** MySQL、Connector/J、MyBatis 和时间处理器的实际版本；JVM 与数据库会话时区；实验代码与原始结果。记录中“LocalDateTime 一定转换”“统一时区即低风险”等概括不能直接提升为通用结论。7/8 小时修正范围也需要按历史日期和实际写入路径核对。

建议文件：`docs/lab-tech-exploration/database-middleware/jdbc-timezone-history-data-repair.md`。

### A3：接口超时后，服务为什么还在工作

**读者问题：** 定时任务已经失败了，为什么服务还在不停执行 SQL？分页查询为什么还会产生几万参数的请求？

**原始材料：** S023、S024、S032。

S024 记载一次约三万条用户数据的 RPC 同步，处理超过两小时，随后改为每批 50 条并优先处理较新的数据。另两份材料分别涉及 CRM 查询与教育系统按订单号查询，SQL 附件中的单个 `IN` 列表按逗号分隔统计，分别约有 17,448 和 16,993 项。

这几份记录属于同类问题，不能未经核实合并成同一次事故。

**建议结构：** 调用方失败与服务端执行状态 → 确认输入规模 → 大 SQL 与长任务的形成 → 区分分页、批量上限和总量查询 → 分批方案的验证 → 部分失败和重复执行的问题。

**待补材料：** 调用配置、修改提交、任务重入与失败恢复行为。每批 50 条是当时的选择，不能写成通用最优值；“分页后数据库没有压力”也需要实测。

建议文件：`docs/lab-tech-exploration/engineering-practice/bounded-batch-rpc-and-large-in-query.md`。

### A4：看起来像下午五点报价变了

**读者问题：** 同一个机构和金额，为什么会出现不同报价？客服观察到的时间规律是不是根因？

**原始材料：** S096、S132、S188、S189。

最初记录描述下午五点后价格不同，后续定位指向登录用户的 `project_type`：医疗类型用户在教育机构下单，却带入了医疗报价。2026-01-05 和 01-06 的发布记录进一步留下了调整方向，最终描述是使用机构或订单的业务类型，而非请求路径。

**建议结构：** 保留最初观察 → 对比报价配置与请求上下文 → 找到业务类型来源 → 为什么用户属性不能决定机构业务 → 修正后跨账号、跨入口验证。

**待补材料：** 报价选择代码、配置 ID 和同条件对照测试。写作应交代早期方案提到请求头，而后续发布记录指向机构或订单，核对最终实现。不要把“下午五点”写成已被证明的因果关系。

建议文件：`docs/lab-tech-exploration/engineering-practice/pricing-business-type-source.md`。

### A5：一个手机号承担三种身份

**读者问题：** 客服代学生下单时，业绩算给谁、谁可以查看订单、联系谁，能不能用同一个手机号表达？

**建议结构：** 最初统计需求 → 新增使用场景暴露歧义 → 三种身份分别回答什么问题 → 列表、编辑、导出和历史数据的影响 → 已回滚方案留下的认识。

### A6：智能客服怎样接入业务系统

**读者问题：** 聊天中说出的机构简称、币种俗称和费用名称，怎样才能进入一个需要 ID、枚举和证明材料的下单接口？

**原始材料：** S265、S264、S266、S267、S281、S282、S283、S203、S204。

已有记录覆盖字段转换、多个接口之间的依赖、机构/币种/费用别名、后台管理，以及材料分类和人工上传的流程限制。发布记录确认过别名管理发布与数据导入，但不能据此推断智能客服已实现全流程自动处理。

**建议结构：** 从一段用户表达开始 → 名称与 ID 的转换 → 枚举和必填字段校验 → 别名冲突与维护 → 文件材料边界 → 人工接续业务流程。

**待补材料：** 完整调用示例、歧义输入的处理、别名唯一性及未匹配时的反馈。不要虚构模型训练、提示词、识别准确率或全自动支付能力。

### A7：把一个出款选项拆成两个字段

**读者问题：** “某渠道电汇”和“某渠道刷卡”为什么后来需要分开表示？旧订单里已经停用的渠道应怎样保留？

**原始材料：** S174。

**待补材料：** 发布次序、空值与未知值的处理、迁移前后核对结果。原始数量可说明分布；正式文章可以使用保留结构的示例数据。

### A8：十四秒的下单请求慢在哪里

**读者问题：** 去掉一次远程登录，为什么没有明显解决下单慢的问题？

**原始材料：** S284；系统部署背景可参考 S217。

记录中的一次生产请求约 14.54 秒，测试请求约 1.37 秒。其分析把生产两次报价分别计为约 5.70 秒、5.03 秒，合计约占 74%。记录也指出第二次报价再次执行部分计算链路。

**建议结构：** 最初怀疑 → 为每个阶段记录耗时 → 找到主要耗时段 → 对照测试环境 → 分开调查数据库访问与重复计算 → 记录仍未收敛的问题。

**待补材料：** 正文引用的下单日志 TXT 没有出现在该 ZIP 的附件中，现包只有两张图片；需要找回日志并复算阶段数据。数据库访问耗时不能直接等同于数据库服务器执行 SQL 的耗时。跨地区访问、缓存、连接与执行计划均不能仅凭该对比认定为根因。当前适合写调查记录，不能承诺已经优化到某个水平。

建议文件：`docs/lab-tech-exploration/engineering-practice/order-pricing-latency-investigation.md`。

## 不建议直接展开成独立文章的记录

- 单一客户的报价、账号、专属链接配置：多数是具体操作清单。可以汇总观察配置维度和重复工作，再决定是否写“配置管理如何产品化”。
- 只有标题、目标或外部链接的记录：例如连接池替换、某些定时任务优化，没有过程和结果，暂不足以形成复盘。
- 大段银行接口报文和联调报告：可支撑已存在的渠道接入文章，但仅有成功报文不能说明设计取舍或生产成熟度。
- 发布记录本身：优先作为上线状态和验证结果的佐证，不按发布日期各写一篇。
