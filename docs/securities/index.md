# 证券工程

## 为什么有证券工程？

最初，我只是希望利用自己掌握的软件开发技术，解决证券使用过程中遇到的一些实际问题。

从最早的程序化交易，到后来的成交记录管理、融资负债、市场数据采集和分析功能，随着使用过程中不断出现新的需求，相关软件也在持续演进。

这些功能并不是一开始就完整规划好的。

很多设计来自实际使用中遇到的问题。有些方案能够满足当时的需求，但随着业务变得复杂，原来的模型又可能暴露出新的限制。

因此，我希望把这些开发经历记录下来。

不仅记录最终实现了什么，也记录为什么需要这个功能、当时如何设计、遇到了哪些问题，以及后来为什么需要调整。

**这里关注的不是如何交易证券，而是如何通过软件工程解决证券业务中的实际问题。**

## 内容分类

证券工程计划按照业务能力划分为六个方向。

| 分类 | 目录 | 内容范围 |
|---|---|---|
| 系统建设 | `system/` | 系统起源、整体架构、技术选型与演进过程 |
| 证券交易管理 | `trading/` | 自动委托、成交回报、交易流水、中和模型、成交归档 |
| 融资业务 | `margin/` | 融资负债、还本还息、合约关联、生命周期管理 |
| 市场数据 | `market-data/` | 行情采集、历史数据、数据同步、存储与一致性 |
| 市场分析 | `analysis/` | 技术指标、市场广度、指数分析、数据聚合与计算 |
| 期权业务 | `options/` | 期权成交记录、开平仓配对、到期处理等 |

以上是长期内容规划，不代表对应的文章已经完成，也不代表相关功能全部实现。

**目录按实际内容逐步建立，不提前创建空目录和占位文章。**

证券交易管理方向可以先阅读[《从零打通 Java、Python 与 QMT 的真实证券交易链路》](/securities/trading/programmatic-t-trading)，了解从人工做 T 到程序化委托执行的实现过程。

## 记录什么？

这个专题主要关注三个方面。

### 真实的业务问题

从实际使用中发现问题，而不是为了使用某种技术而设计功能。

例如，一笔买入成交为什么不一定对应一笔卖出成交？券商提供的融资流水为什么难以直接关联到原始借款？

这些问题背后往往涉及具体的业务规则，需要先理解业务，再考虑技术实现。

### 工程设计与实现

记录如何将业务问题转化为软件功能，包括数据模型、系统边界、外部接口、业务状态、计算逻辑以及验证方式。

技术栈只是实现手段。

相比使用了什么框架，我更希望记录为什么采用某种设计，以及这种设计在当时解决了什么问题。

### 持续演进与复盘

最初能够正常运行的方案，不一定能够满足后来的需求。

随着真实数据和业务场景不断积累，原来的设计可能需要扩展、修改，甚至被替代。

因此，除了最终实现，也会保留有代表性的历史方案、遇到的问题和调整依据。

## 记录原则

本专题基于真实开发经历、代码、数据和使用过程中发现的问题。

区分已经实现的功能、正在进行的实验，以及尚未落地的设计。

不因为后来的方案更完善，就否定早期方案在当时的价值；也不因为某个功能能够运行，就认为它已经没有改进空间。

这里不提供证券投资建议，也不以展示交易收益为目标。

**希望保留下来的，是一个软件系统在真实业务需求推动下，不断建设、验证和演进的过程。**
