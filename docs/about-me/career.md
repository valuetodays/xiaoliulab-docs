# 工作经历（2014—至今）

2014年春天，我离开河南新乡，前往北京寻找工作。

大学期间，我读的是英语师范专业，但已经自学了几年计算机，希望能够从事软件开发。

当时北京有几位亲戚。此前聊天时，他们提到北京的工作机会比较多，也建议我过去试试。

于是，我来到了北京。

从2014年到现在，我先后在北京、南京和杭州生活、工作，接触过保险、支付、金融营销等不同业务。

这些年里，我也在工作之外持续学习、编写程序，并逐渐开始研究证券市场。

## 一、北京：第一份软件开发工作（2014—2016）

### 从电脑店开始

刚到北京时，我住在昌平史各庄附近。

最初，我并没有直接找到软件开发工作，而是在一家兼营电脑维修和复印业务的小店工作。

日常主要是给客户重装操作系统、处理软件故障。硬件维修有专门的师傅负责。

这份工作持续了大约半个月到一个月。

店里有电脑，也能上网。工作之余，我会通过智联招聘等网站投递 Java 开发岗位。

后来，我接到了一些招聘人员的电话，开始参加面试。

### 第一次 Java 开发面试

我通过一家提供人员外派服务的公司，获得了某大型保险公司的面试机会。

面试前，我学习过 Java、JDBC、数据库和 SSH 等技术，也搭建过开发环境，尝试运行一些框架程序。

但此前还没有真正参与过企业软件项目。

面试中有一道题，我一直记得。

大意是：

两个人同时打开同一条数据。B先修改并保存，A出去抽了一支烟，回来后又保存了自己此前打开的页面。

怎样避免A的操作把B已经修改的数据覆盖掉？

我当时想到了乐观锁，可以通过版本号等方式判断数据在读取后是否被其他人修改。

这道题让我印象很深。至于它在最终录用决定中起了多大作用，我并不知道。

那次面试通过后，我进入这家保险公司的项目组，开始从事 Java 开发工作。

最初的月工资大约是3000元，后来陆续有所调整。

### 第一次接触企业软件开发

项目组位于北京的一处办公园区。

我从住处步行过去，大约需要半小时，途中还会经过一段铁路线。

刚加入项目组时，前两天主要是按照文档搭建开发环境，把已有项目运行起来。

熟悉环境后，我参照项目中的代码，尝试编写了一个带有数据库增删改查功能的小程序。

后来逐渐开始参与实际业务。

当时接触的系统主要围绕保险业务，包括产品信息管理、续保提醒、客服坐席及录音质检等。

例如，续保业务需要识别即将到期的保单，再根据客户是否续保，进入不同的提醒或跟进流程。

技术上，当时使用的是传统 Java Web 开发方式。

项目中有不少 Action 类和 XML 配置，使用过 Apache Ant 构建脚本，也通过 Web Service 与其他系统交互。

开发和发布过程中的一些操作比较繁琐。

工作之外，我继续阅读 Java 相关书籍，接触 Maven、Spring MVC 等技术。

其中，《Spring in Action》给我留下了比较深的印象。我开始尝试使用注解等方式开发 Web 应用，并在自己的练习项目中验证。

2016年，我决定离开。

主要原因是收入方面的考虑。工作两年多以后，我觉得自己的技术能力有了增长，希望获得与之更匹配的报酬。

同时，我也希望接触不同的技术环境和开发方式。

## 二、北京：支付公司与工程实践（2016—2018）

2016年，我进入北京一家小型支付公司。

当时选择这份工作，主要考虑的是工作地点和收入，并没有制定什么复杂的职业发展计划。

公司规模不大，开发人员也不多，平时可以直接坐在一起讨论问题。

### 商户收款业务

公司主要面向商户提供收款服务。

例如，商户可以使用电子二维码收款，消费者扫码完成支付，再通过商户端查看交易记录、收入统计和提现信息。

我参与过商户管理、交易记录、报表、提现，以及不同支付渠道接入等功能的开发和维护。

当时需要与渠道 A、渠道 B 及其他合作渠道对接（合作渠道名称已匿名化）。

很多功能是在原有系统的基础上持续开发和改造的。

除了业务开发，我还花了不少时间改善日常开发和发布方式。

### 从手工整理文件到自动打包

刚进入公司时，有一种发布方式让我印象很深。

每次上线，开发人员需要回忆本次修改过哪些文件，再把对应的 `.class`、`.properties` 等文件整理出来，按照原来的目录结构打包交给运维。

运维人员备份旧文件，手工覆盖，再重启服务。

如果少放了某个文件，就需要重新查找、补充、发布。

这个过程很繁琐，也容易遗漏。

当时我已经在个人服务器上尝试过部署 Java 程序，对这种手工整理文件的方式不太满意。

于是，我利用业余时间编写了一个小工具。

工具根据配置的上次发布时间，读取 SVN 中相关时间范围内的提交记录，再整理这些提交涉及的文件，从本地项目中收集对应的编译结果，生成保留目录结构的增量发布包。

这样就不必完全依赖开发人员凭记忆查找修改过哪些文件。

这个工具后来用于团队的日常发布。

现在回头看，如果当时直接采用完整 WAR 包交付，也许能省掉不少中间步骤。

但在当时，我首先想到的是把已经存在的手工流程自动化。

### Spring MVC、Maven 和 Jenkins

后来，公司准备开发一个新工程。

我想起了此前阅读的《Spring in Action》，以及自己练习过的 Spring MVC。

于是，我向领导建议，可以尝试使用 Spring MVC，减少旧框架中繁琐的 Action 和 XML 配置。

领导希望先看看实际效果。

因为此前已经做过相关 Demo，我便直接展示了注解路由、参数处理等写法，以及它们与原来开发方式的区别。

最终，领导同意了这个方案，并把新工程交给我负责。

这件事让我体会到了“学以致用”：之前通过阅读和个人练习掌握的知识，终于有机会解决实际工作中的问题。

新工程开始使用 Spring MVC 和 Maven，发布方式也逐渐从整理零散的 class 文件转向构建完整的 WAR 包。

随后，我又与运维同事一起尝试了 Jenkins。

通过配置，可以让 Jenkins 从 SVN 获取代码，调用 Maven 构建，再执行部署和应用启停脚本。

后来我们还自行搭建过 GitLab，用一个测试项目验证 Jenkins 从 GitLab 拉取代码的流程。

公司的正式业务项目仍然使用 SVN。

这些改进是我和运维同事在日常工作中逐步尝试、完成的。

2018年，我结束了在这家公司的工作。

这两年多的支付业务开发经历，让我积累了不少实际经验。

## 三、北京与南京：近七年的工作经历（2018—2025）

2018年，我加入一家金融营销技术公司。

这是我至今任职时间最长的一家公司。

最初在北京工作，2021年转到南京分部，直到2025年离开。

虽然工作城市发生过变化，但始终属于同一家公司，也一直与原来的技术团队保持协作。

### 金融机构的营销系统

公司主要为银行、证券等机构提供营销技术服务。

当时的产品主要部署在客户自己的环境中，需要与客户已有的数据和业务系统结合使用。

不同机构的数据结构可能不同，系统需要通过配置，将客户实际的数据字段映射到产品所理解的用户、事件等业务概念。

在这些数据基础上，可以根据用户属性、历史行为等条件筛选人群，再通过营销活动设置消息触达、等待时间、事件判断和不同的流程分支。

活动运行后，还可以进行统计和效果分析。某个活动节点上的用户集合，也能够保存为新的可复用人群。

我参与了这些功能的开发，也参与了公司核心产品的一次较大规模改版。

印象中，原来的技术体系涉及 Dubbo、AngularJS 等，后来逐步转向 Spring Boot、Spring Cloud，业务模型与前后端代码也做了较多调整。

这次产品改版由北京、上海等地的同事共同完成。

### 一次单点登录接入

在这家公司工作期间，有一次券商客户的单点登录需求让我印象很深。

客户希望员工通过自己的统一登录入口进入我们的系统，同时保留原有账号密码登录方式。

我独立完成了这部分接入工作。

整个过程需要在客户登录页面和我们系统之间完成跳转，再利用同一主域名下不同子域名之间的 Cookie 共享机制取得登录状态，由后端调用客户提供的接口核验身份。

确认身份后，再与系统中的本地用户建立对应关系，完成登录。

这次接入既需要满足客户的统一认证要求，也需要兼容原有登录方式。

### 单元测试与代码质量

在此期间，我还有机会尝试此前一直感兴趣的一些工程工具。

例如 JUnit 4、JUnit 5、JaCoCo 和 SonarQube。

我尝试给自己负责的代码编写单元测试，查看代码覆盖率，并使用静态分析工具检查重复代码、异常处理、日志使用和方法复杂度等问题。

这些工具能够正常运行，也让我看到了原有代码中一些值得关注的问题。

不过，整个团队并没有因此形成统一、持续的测试实践。

这些尝试更多保留在我自己负责的代码和个人项目中。

### 为什么在这里工作了这么久

回想这段工作经历，我最认可的是当时的技术团队，尤其是我的直属领导。

他懂技术，也愿意讨论实际问题。

有时我们对某个需求或实现方案有不同看法，可以直接讨论技术上的取舍。

我并不觉得技术领导必须亲自编写每一段代码，但希望他能够理解开发中的关键问题，知道哪些事情简单、哪些事情需要时间。

那段时间，我与测试、产品、开发等同事的合作总体比较顺畅，也很少因为工作需要长期加班。

除了技术，我们还会聊历史、诗词和《三国演义》。

有一次，领导谈起杜牧的《赤壁》：

“东风不与周郎便，铜雀春深锁二乔。”

他还转述过儿子对这句诗的一种理解：一个人的成功，有时也受到环境和时机的影响；没有遇到合适的时机，并不一定意味着这个人完全没有能力。

我记得当时觉得这种阅读角度很有意思。

这些工作之外的交流，也是我对那段团队生活的记忆之一。

### 2021年，从北京到南京

2021年，我从北京转到了公司的南京分部。

这是我主动提出的选择，不是公司要求我必须离开北京。

在北京生活了七年多以后，我开始考虑换一个城市。

在北京的最后几年，通勤单程大约一小时。我也不太适应北京较为干燥的空气，以及夏季炎热、冬季寒冷的气候。

同时，我开始考虑以后在南方生活和安家的可能性。

我比较过几个南方城市，最后选择了南京。

南京已有公司的办公地点，因此可以在不更换工作的情况下尝试另一座城市。

到南京以后，我仍然与北京、上海的同事协作，主要工作内容和直属领导并没有发生太大变化。

生活上的改变却比较明显。

南京的房租比我在北京时低，从住处到公司，步行大约半小时，骑自行车只需要十几分钟。

每天花在上下班路上的时间减少了不少。

南京还有一个地方让我印象很深：江东中路。

第一次注意到“江东”这个名字，我就想到了项羽无颜见江东父老的故事，也想到了孙策、孙权和三国时期的东吴。

以前在书里读过的词语，突然出现在日常生活经过的道路上，是一种很有意思的体验。

### 2025年，离开南京

2025年，我结婚了。

妻子希望以后在杭州生活和发展，我也愿意与她一起在那里安家。

当时我的想法很简单：

**“她去哪儿，我去哪儿。”**

如果原公司在杭州也有合适的办公地点，我可能会考虑继续留在原公司。

但实际并没有这样的安排。

于是，2025年，我离开了工作多年的团队，准备到杭州开始新的生活。

这次离职，最主要的原因是生活城市的变化。

## 四、杭州：新的工作与生活（2025—至今）

2025年，我来到杭州。

在原公司待了很长时间以后，我已经很久没有正式参加面试。

此前几个月，我曾经尝试投递一些简历，主要是想重新熟悉面试过程。

真正来到杭州后，我参加了两家公司的面试。

其中一家是游戏公司，另一家就是我现在工作的公司。

当时我希望尽快把工作确定下来，最终选择了现在的岗位。

### 接手一个运行多年的系统

新工作主要是接手一个已经运行多年的支付相关业务系统。

与之前参与新系统研发、产品重构的经历不同，这一次，我更多是在理解和维护已有系统。

刚接触时，能够参考的文档比较少，很多业务关系需要从代码、数据库和实际运行情况中寻找。

有时需要根据错误日志定位代码，再追踪不同功能之间的数据流转。

有时表面上只是一个简单的业务操作，背后却涉及多个模块和数据关系。

我用了大约两个月，逐渐梳理出系统的主要业务流程，此后继续进行维护和功能开发。

这也是我软件开发经历中的另一种工作方式。

到现在，我仍然在杭州工作和生活。

对于这段仍在继续的经历，我暂时不打算作太多总结。

## 五、工作之外的学习与个人实践

这些年里，除了工作，我也持续阅读和尝试自己感兴趣的事情。

如今，我在业余时间投入较多精力的是金融研究和个人程序开发。周末有空时，我也喜欢爬山。

其中一些长期坚持的实践，后来逐渐发展成了个人项目。

### 从阅读到证券市场

大学期间，我经常去图书馆借书。后来整理当年的借阅记录，发现留下了两百多条记录。

工作以后，我仍然保持着阅读的习惯，只是获取书籍的方式逐渐从借阅变成了自己购买。

2014年至2018年间，我购买了不少实体书，累计花费印象中约有5000元。

阅读的范围也很广，除了计算机技术，还包括历史、心理学、社会和理财等方面。

其中，《富爸爸穷爸爸》《小狗钱钱》是给我留下较深印象的两本书。

当时我开始接触一些关于资产、负债、现金流和财务独立的观点。

后来，我逐渐尝试定期理财、场外基金，再到场内基金和证券交易。

具体是哪一年开始第一笔场内交易，现在已经记不清了。

我对交易产生兴趣的一个原因，是价格变化带来的差价。

例如，假设手里持有某只价格为1.001元的基金，先以1.001元卖出，再以1.000元买回。

如果两笔交易都能成交，在不考虑费用的情况下，份额不变，就可以获得每份0.001元的差价。

刚想到这种操作时，我甚至想过：

假如一天能做一万次、十万次，会怎么样？

后来上网查资料，才逐渐了解到这种围绕已有持仓反复买卖的操作通常被称为“做T”。

当然，现实中并不是想卖就能卖、想买就能买。手续费、成交量、价格变化和交易规则，都会限制实际结果。

但最初这种可以计算的价差关系，让我产生了继续研究的兴趣。

### 从手工交易到程序化尝试

随着交易经验增加，我开始思考，能不能把一些重复操作交给程序完成。

最早的尝试，并不是通过券商提供的正式交易接口。

我使用过 Win32、Spy++ 和一些 Windows 自动化工具，研究证券交易客户端中的窗口和输入控件。

通过定位窗口、填写参数和模拟点击，我曾经成功向交易客户端发出委托。

当时还专门录制过操作视频，发给朋友看。

不过，这种方式有明显的局限。

程序能够模拟点击，并不意味着可以可靠地知道订单是否成交，也很难及时获取完整的订单和成交状态。

后来，我接触到 QMT、MiniQMT 等程序化交易工具，开始使用更合适的接口获取行情、发送委托和处理回报。

再往后，这些尝试逐渐扩展成一系列个人系统。

例如，采集 ETF 和指数行情，计算技术指标，记录交易流水，自动配对买卖记录，统计盈亏，设置目标价格提醒，以及根据条件执行部分交易操作。

我也开始研究融资交易、ETF期权、分红复投和低频机会交易等不同问题。

最初只是想研究价差，后来却发现，想判断某种交易方法有没有实际效果，就需要历史数据、统计样本和回测；想减少重复操作，又需要软件自动化。

随着研究继续深入，还会遇到仓位管理、风险控制、心理决策和长期现金流等问题。

一个问题逐渐引出了更多问题。

### 小刘实验室

在学习编程和研究交易的过程中，我也长期购买过云服务器、域名，部署和测试自己的程序。

最初并没有想好要建立一个内容丰富的个人网站。

后来，一些实际完成的功能开始被整理成文档，逐渐形成了今天的小刘实验室。

其中，微信支付是一个比较早的例子。

我不太喜欢那种看完教程、写了很多代码，却始终不知道最终效果能否运行的学习过程。

因此，做微信支付实验时，我选择先让真实支付流程能够运行，再整理相关的接入步骤和技术说明。

我把这种做法理解为：

**“把结果前置，你先看到效果，再去写代码。”**

后来，网站中加入了一个一分钱的真实微信支付体验。

访问者可以实际发起支付，完成后阅读背后涉及的技术环节，支付金额也会按照设定流程退还。

2026年11月2日，第一次有一位不认识的访客真正完成了这笔支付。

此前已经有人访问过这个功能，但一直没有人实际付款。

发现终于有人愿意尝试时，我很惊喜。

这也意味着，原本只是我自己用来学习和验证技术的功能，开始有机会帮助其他人理解真实的支付流程。

除了微信支付，网站还逐渐增加了软件工程、证券研究、个人实验，以及一些与生活有关的文章。

写作方式同样在发生变化。

以前主要依靠自己查找资料、尝试和记录。后来，我开始使用 AI 协助整理文章、分析问题、检查事实和发现遗漏，再根据实际经历和实验结果进行修改。

我也希望以后有人能够带着真实的软件研发问题来交流。

比如：

“我在软件研发中遇到了这个问题，看了网上教程还是不明白，你能不能帮我研究一下？”

目前这样的交流还不多，但如果能够通过实际研究解决一个具体问题，再把过程整理成可复现的文档，我觉得是一件值得做的事情。

这篇《工作经历》，以及前面的《童年和求学经历》，也是通过不断回忆、整理和修订逐渐形成的。

## 写在最后

从2014年到现在，我在北京、南京和杭州生活过，也接触了不同的行业和工作方式。

最初在电脑店帮人安装系统，后来通过外派进入保险业务的 Java 项目组，再到支付系统、金融机构营销系统，以及现在维护的业务系统。

工作之外，我也一直在学习和尝试新的事情。

有些尝试只持续了一段时间，有些则发展成了今天仍在继续的项目。

回头看，这些年并不是按照一份事先制定好的计划逐步展开的。

换工作时，我会考虑收入、团队和工作环境；选择城市时，也会考虑通勤、生活和家人的安排。

如今，我仍然有想继续研究的问题，也还有想做的事情。

至于后面的经历，就留待以后继续记录。
